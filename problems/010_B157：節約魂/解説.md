# B157:節約魂 — 解説とアルゴリズム整理

- 問題URL: https://paiza.jp/challenges/794
- ランク: B
- 制限: 5.0 秒 / 512 MB
- コード: [Program.cs](Program.cs) … 提出版【A】と改良版【B】を隣り合わせで対比

## 問題

**入力**

```
N K
p_{1,1} ... p_{1,K}
...
p_{N,1} ... p_{N,K}
```

**条件**

- 1 ≦ N, K ≦ 50
- 1 ≦ p_{i,j} ≦ 1000
- **p_{i,k} ≠ p_{j,k}** … 同じ野菜が他店と同値になることはない

**出力** — 合計金額が最安になるように買うとき、回る必要のある最小店舗数

---

## 問題の骨格（ここが一番の学びどころ）

「同じ野菜が他店と同値にならない」条件のおかげで、**各野菜の買う店が一意に確定する**（最安の店がちょうど1つしかない）。つまり選択の自由度がゼロで、最適化・探索の余地がない。答えは「各列の argmin 行が何種類あるか」を数えるだけになる。

もしこの条件が無かったら、各野菜に「最安の店の集合」ができ、「最小個数の店で全野菜をカバーせよ」= **集合カバー問題（NP困難）** になる。問題文のあの一文はそれを回避するために置かれている。

→ 条件を読んで「じゃあ一意だ」と判断できたなら、それが正しい読み方。

# O 記法とは（前提知識）

## 何を測っているのか

「このコードは速いか？」を秒で測ると、CPU・言語・その日のマシンの機嫌で数字が変わる。比較に使えない。

そこで測るものを変える。**「入力が大きくなったとき、やるべき手順の回数がどう増えるか」** だけを見る。増え方の形は、どのマシンで走らせても変わらないから。

入力の大きさを表す変数を `N`（今回は店の数 `N` と野菜の種類 `K` の2つ）とし、手順の回数を `N` の式で表したものが **計算量**。それを「増え方の形」だけに削ったのが **O 記法**（オーダー記法、ランダウの記号）。O は Order（次数・位）の頭文字。

## 数え方

基本操作（代入、足し算、比較、配列アクセス）1回を「1」と数える。あとはループの構造を見るだけ。

```csharp
int s = 0;                          // 1回      → O(1)   … 入力サイズに関係なく一定

for (int i = 0; i < N; i++) s += i; // N回      → O(N)   … 1重ループ

for (int i = 0; i < N; i++)                  // ┐
    for (int j = 0; j < K; j++) s += i * j;  // ┘ N*K回  → O(NK)  … 入れ子は掛け算

for (int i = 0; i < N; i++) s += i;          // ┐
for (int i = 0; i < N; i++) s += i;          // ┘ 2N回   → O(N)   … 並ぶだけなら足し算
```

**入れ子（ネスト）は掛け算、並列に並ぶのは足し算。** これがオーダーを読む基本。

## 定数倍と低次項は捨てる

`3NK + 5K + 100` は `O(NK)` と書く。3倍も、`5K` も、`100` も消える。

- **低次項を捨てる理由**: N, K が大きくなると `NK` が他を完全に飲み込む。N=K=1000 なら `3NK`=300万 に対し `5K`=5000 は 0.2%以下。
- **定数倍を捨てる理由**: 2倍・1.5倍という差はCPU・言語・書き方で簡単にひっくり返る。一方 `NK` と `N²K` の差は、どんなに速いマシンを持ってきても N を大きくすれば必ず負ける。**ハードや言語に依存しない本質的な差だけを残すためのフィルタ**がO記法。

だから `2 × O(NK) = O(NK)`、`O(NK) + O(NK) = O(NK)` になる。**「2倍遅い」はO記法では表現されない**（そこは実測の世界）。

正式な定義はこう：

> `T(N) = O(f(N))` ⟺ ある定数 `c` と `N₀` が存在して、`N ≧ N₀` のすべてで `T(N) ≤ c·f(N)`

`c` が「ある定数」なので、**定数倍は最初から定義に飲み込まれている**。`T(N) = 3NK` なら `c = 3` を取れば `T ≤ c·NK` が成り立つ、という理屈。

## 「定数倍」とは何か、なぜそれが「改善」なのか

実際の実行時間はだいたい **`実行時間 ≒ c × f(N)`** という形をしている。

- `f(N)` … **増え方の形**（`NK` とか `N²` とか）＝ オーダー。O記法が表しているのはこっち。
- `c` … **その形にかかる係数**。これが「**定数倍**」。O記法が捨てたほう。

`c` の中身は「1要素あたり何回操作するか」「1回の操作がどれだけ重いか」。たとえば同じ `O(NK)` でも、1マスあたり2回なめるコードと1回で済むコードでは `c` が2倍違う。

**「定数倍の改善」= `f(N)` の形は変えずに `c` を小さくすること。** グラフで言えば、曲線の**形はそのままで傾きを下げる**イメージ。

なぜ改善と呼べるか — **`c` は実測時間に直接効くから**。O記法が「同じ `O(NK)` だ」と言って区別しなくても、現実の実行時間は `c × NK` なので、`c` が半分になれば実行時間も半分に近づく。O記法は比較のための道具であって、「O記法で差が出ない = 速くならない」ではない。

オーダーの改善との違いはここ：

| | 何が変わるか | N=50 のとき | N=1000 のとき | N=10⁶ のとき |
|---|---|---|---|---|
| **定数倍の改善**<br>2NK → NK | 傾きだけ。差は**常に一定の倍率** | 2倍速い | 2倍速い | 2倍速い |
| **オーダーの改善**<br>O(N²) → O(N log N) | 形そのもの。**N が大きいほど差が開く** | 約9倍速い | 約100倍速い | 約5万倍速い |

だから優先順位は **まずオーダー、次に定数倍**。オーダーが1段違えば定数倍の努力は無意味になる（N が大きければ「10倍雑に書いた `O(N log N)`」が「限界まで詰めた `O(N²)`」に勝つ）。逆に、**オーダーが最適で下げようがないときに初めて定数倍の勝負になる** —— この問題はまさにその状態（下限 `Ω(NK)` に到達済み）なので、【B】の改善は全部そこの話。

定数倍を下げる代表的な手口（【B】でやっているもの）：

| 手口 | 中身 | このコードでの例 |
|---|---|---|
| 1パス化 (single-pass) | 2周する処理を1周にまとめる | 読み込みと最小値探索を同時にやる（差分2）。→ [下の節](#1パス化と-loop-fusionループ融合) |
| 割り当てを減らす | ヒープ確保とGCの負担を消す | `HashSet` → `bool[]`（差分3） |
| データ構造を軽くする | 汎用構造をやめて値域に合った専用の形にする | ハッシュ集合 → 直接アドレス表（差分3） |
| メモリ使用量を削る | 触る範囲が狭いとCPUキャッシュに載って速い | `int[N,K]` → `int[K]`（差分1） |

ただし **`c` は「操作の回数」だけでなく「操作の重さ」も含む**ので、回数を半分にしても時間が半分になるとは限らない。このコードで走査回数が 2NK→NK になっても実測が2倍にならないのは、消えた側（`if` 比較）が残る側（`int.Parse`）よりずっと軽いから。ここがO記法から一番見えにくい部分。

## 増え方の実感

N が10倍になったとき何が起きるか。これが分かるとオーダーの重みが体感できる。

| オーダー | N=10 | N=100 | N=1,000 | N=1,000,000 | 呼び名 |
|---|---|---|---|---|---|
| `O(1)` | 1 | 1 | 1 | 1 | 定数時間 |
| `O(log N)` | 3 | 7 | 10 | 20 | 対数時間 |
| `O(N)` | 10 | 100 | 1,000 | 10⁶ | 線形時間 |
| `O(N log N)` | 33 | 664 | 9,966 | 2×10⁷ | 準線形 |
| `O(N²)` | 100 | 10,000 | 10⁶ | 10¹² | 二乗時間 |
| `O(2^N)` | 1,024 | 10³⁰ | 論外 | 論外 | 指数時間 |

`O(log N)` は N が100万倍になっても20倍しか増えない（二分探索がこれ）。逆に `O(2^N)` は N=100 で宇宙の年齢では終わらない。

## 代表的なオーダーと例

| オーダー | 例 |
|---|---|
| `O(1)` | 配列の添字アクセス、`Dictionary` の参照、四則演算 |
| `O(log N)` | 二分探索、平衡二分木の挿入・検索、ヒープの push/pop |
| `O(N)` | 線形探索、最大/最小を探す、配列を1周なめる ← **今回やっていること** |
| `O(N log N)` | 比較ソート（`Array.Sort`、マージソート） |
| `O(N²)` | 全ペアの総当たり、バブルソート、素朴な二重ループ |
| `O(2^N)`, `O(N!)` | 部分集合の全列挙、順列の全列挙 |

## 実務・競プロでの目安

ざっくり **1秒で 10⁸〜10⁹ 回**の基本操作、と見ておく。paiza の制限は5秒なので、操作回数が 10⁸ 程度までなら概ね通る。

そこから逆算して、**制約を見ればオーダーの許容ラインが分かる**：

| 制約 | 通せるオーダーの目安 |
|---|---|
| N ≦ 10⁶ 〜 10⁷ | `O(N)`, `O(N log N)` |
| N ≦ 10⁴ | `O(N²)` でもOK |
| N ≦ 500 | `O(N³)` でもOK |
| N ≦ 20 | `O(2^N)` の全列挙が視野に入る |

**今回は N, K ≦ 50 なので NK = 2500。** 何をやっても間に合う。だから100点が出た。制約の小ささは「素直に書いていい」というヒントでもある。

## 落とし穴

- **`O` は上限しか言っていない**。`O(N)` のコードを `O(N²)` と書いても定義上は嘘ではない（正確でないだけ）。ぴったり言いたいときは `Θ`（シータ）を使う。
- **オーダーが同じでも速さは違う**。定数倍と「1回の操作の重さ」が隠れている（このコードの【A】vs【B】がまさにその例）。
- **最悪／平均／最良を区別する**。クイックソートは平均 `O(N log N)` だが最悪 `O(N²)`。断りがなければ普通は最悪計算量を指す。
- **中で呼んでいるメソッドの計算量を忘れない**。ループが1重でも、中で `List.Contains`（`O(N)`）や文字列連結（`O(長さ)`）を呼べば全体は `O(N²)`。「ループの数」ではなく「操作の総回数」を数える。
- **時間だけでなくメモリにもオーダーがある**（空間計算量）。今回の【A】はメモリ `O(NK)`、【B】は `O(N+K)`。

## 仲間の記号

| 記号 | 読み | 意味 |
|---|---|---|
| `O(f)` | オー | **上限**。せいぜい f の定数倍（f 以下の増え方） |
| `Ω(f)` | オメガ | **下限**。少なくとも f の定数倍（f 以上の増え方） |
| `Θ(f)` | シータ | **上下ぴったり**。`O` と `Ω` の両方が成り立つ |
| `o(f)` | スモールオー | 厳密に f より小さい（定数倍でも追いつけない） |

`Ω` は「どんなアルゴリズムでもこれ以下にはできない」という**限界の証明**に使う。次の節で「この問題の下限は `Ω(NK)`」と言っているのがそれ。

## この問題の計算量

N×K 個の数値を全部読まないと答えが確定しない（1つ読み飛ばすと最安値が変わり得る）ので、**下限は Ω(NK)**。よって【A】【B】どちらも時間的には最適で、これ以上オーダーは下がらない。改善余地は定数倍とメモリだけ。

| | 走査回数 | 時間 | メモリ |
|---|---|---|---|
| 【A】提出版 | 約 2NK | O(NK) | O(NK) |
| 【B】改良版 | 約 NK + K | O(NK) | O(N+K) |

### 差分まとめ

| # | 箇所 | 【A】 | 【B】 | 効果 |
|---|---|---|---|---|
| 1 | 価格の保持 | `int[N,K]` に全部貯める | 列ごとの最小値 `int[K]` 2本 | メモリ O(NK) → O(N+K) |
| 2 | 走査回数 | 読み込みと最小値探索で2周 | 1周に融合（loop fusion） | 約 2NK → 約 NK |
| 3 | 重複除去 | `HashSet<int>` | `bool[N]` | ハッシュ計算とヒープ確保が不要 |

**注意**: 3つとも O 記法では同じ `O(NK)` に潰れる。定数倍とメモリの改善にすぎない。

差分2の実測効果も2倍にはならない。【A】のパス2は `if` 比較だけで、`int.Parse`（文字列→整数変換）を含むパス1より一桁以上軽く、支配項ではないため。**O 記法が隠している「1回の操作の重さ」がここに出る。**
差分3も N ≦ 50 では実測差はまず出ない（手法の違いとして）。

## この問題でやっている操作の名前

- **線形探索 (linear / sequential search)** の一種。値ではなく添字を返すので **argmin**。
- 関数型の言い方では **fold / reduce（畳み込み）**。累積値と次の要素を二項演算で潰していく形。`Enumerable.Min` や `Aggregate` の中身も同じ。
- 比較回数 **n-1** はこれ以上減らせない（最適）。
  - 証明（トーナメント論法）: 「最小でない」と確定させるには各要素が少なくとも1回は比較で負ける必要があり、1回の比較で負けるのは1要素だけ → n-1 回未満では確定不可能。

## argmin とは（arg = argument）

`arg` は **argument（引数）** の略。数学で言う「引数」で、プログラミングの引数と同じ語。関数 `f(x)` について、次の2つは別物。

| 記法 | 読み | 何が得られるか |
|---|---|---|
| `min f(x)` | ミニマム | 最小**値**そのもの |
| `arg min f(x)` | アーグミン | その最小値を与える**引数 x** |

この問題の `f` は「**店の番号 → その野菜の価格**」という関数。入力例1の野菜1（にんじん）なら `f(0)=200, f(1)=180, f(2)=150` なので：

- `min f = 150` … 最安値（円）
- `arg min f = 2` … その値をつけた**店の番号** ← **欲しいのはこっち**

「いくらか」ではなく「どの店か」が答えの材料なので、コードでは価格 (`minPrices`) と店番号 (`minRowIndices`) の**両方**を持って同時に更新する。最大側は同様に `arg max`（アーグマックス）。

```csharp
if (v < minPrices[j])        // 今までの最安値より安かったら
{
    minPrices[j] = v;        // min    を更新（いくらか）
    minRowIndices[j] = i;    // argmin を更新（どの店か）
}
```

機械学習などでも「損失を最小にするパラメータ」を `argmin` と書く。「最小値そのものではなく、それを達成した入力の側が欲しい」という場面は非常に多いので、記法として名前が付いている。

## 重複を数える仕組み（`counted` 配列 / `HashSet`）

各野菜の買う店を並べた `minRowIndices` には**同じ店が何度も出てくる**（1軒で複数の野菜が最安なら、その店は1回しか回らない）。だから「何種類の店が出てくるか」を数える必要がある。

`counted[i]` は「**店 i をもう数えたか？**」のチェックリスト。役割は【A】の `HashSet` と完全に同じで、HashSet が `Add` で勝手に重複を無視してくれるところを、bool 配列では自分で見ているだけ。

入力例1をなぞる（`minRowIndices = [0, 2, 2]`。店2 が2回出てくる）：

| j（野菜） | `minRowIndices[j]` | `counted[minRowIndex]` | やること | `count` |
|---|---|---|---|---|
| 0 | 0 | `false` | 初めて → 印を立てて数える | **1** |
| 1 | 2 | `false` | 初めて → 印を立てて数える | **2** |
| 2 | 2 | **`true`** | **もう数えた店 → 何もしない** | 2 |

→ 答え `2`（店0 と 店2 を回る）。3行目でスキップしているのが重複除去そのもの。

このように「値域が `0..N-1` と分かっている整数の集合」を bool 配列で表す手法を **直接アドレス表 (direct addressing)** と呼ぶ。ハッシュ計算もヒープ確保も要らないので最速だが、値域が広いと配列が巨大になって使えない（そのとき `HashSet` の出番）。

### `minRowIndices` / `minPrices` の値が重複することについて

**どちらも重複し得る。そして意図的。** ここは引っかかりやすいので明示しておく。

**`minRowIndices`** — 1軒の店が複数の野菜で最安なら、その店番号が複数のスロットに入る。極端な例が入力例2で、3種類すべて店0が最安なので `[0, 0, 0]` になる（→ `count = 1`、期待出力と一致）。**この重複を潰すことが答えの計算そのもの**なので、重複は避けるべきものではなく前提。

なお「追加」ではなく**上書き代入**であることに注意。`minRowIndices` は長さ K の固定長配列で、要素数は常に K のまま増えない。`HashSet.Add` のように積み上がっていくわけではない。

**`minPrices`** — 別の野菜同士が同じ値になることもあり得る。問題文の条件 `p_{i,k} ≠ p_{j,k}` が保証しているのは「**同じ野菜 k について、店をまたいだ価格が全部違う**」ことだけで、異なる野菜の間で値が一致するのは禁じていない。入力例2の店1が `200 200 200` なのがその例（各野菜について店をまたいで見れば 100 vs 200、90 vs 200、180 vs 200 なので条件は満たしている）。

そして支障はない。**`minPrices` はループを抜けたあと一度も読まれない**。argmin を求めるための作業用メモにすぎず、答えに使うのは `minRowIndices` だけ。`minPrices` 同士を比較する処理も存在しない。

**列をまたいだ比較は一度も起きない**点も押さえておくとよい。`minPrices[j]` が比べられるのは同じ `j` の中の N 個の値だけで、野菜ごとに完全に独立した N 個の勝ち抜き戦を K 回やっている構造。だから「野菜0の最安値と野菜1の最安値のどちらが小さいか」のような比較はどこにもない。

**【A】との違いは重複除去のタイミングだけ。** 【A】は `minRowIndex` が列ごとに作り直すスカラー変数で（こちらは1個なので単数形が正しい）、1列終わるごとに `HashSet.Add` してその場で除去。【B】は K 個すべて配列に溜めてから最後に `counted` で除去。結果は同じ。

## ソートとの違い ＝ 求める情報量の違い

ソートは全順序（n! 通りの区別）を要求するので比較回数の下限が `log₂(n!) = Θ(n log n)`。max/min は「1個どれか」の情報しか要らないので線形で済む。

→ **必要な情報量が計算量の下限を決める**、という見方で整理できる。

| やりたいこと | 手法 | 比較回数／計算量 |
|---|---|---|
| 最大 or 最小 1つ | 線形走査（畳み込み） | **n-1**（最適） |
| 最大と最小を同時 | ペアワイズ法：2個ずつ比較して勝ち組/負け組に振り分けてから各々走査 | **⌈3n/2⌉-2**（最適）／素直に2周だと 2n-2 |
| 2番目に大きい値 | トーナメント法（優勝者に負けた者だけ再戦） | **n + ⌈log₂n⌉ - 2**（最適） |
| k番目に小さい値（順位統計量） | **Quickselect** | 平均 O(n) / 最悪 O(n²) |
| 同上・最悪保証つき | **Median of Medians**（中央値の中央値） | 最悪 O(n) |
| 上位 k 個 | サイズ k の**ヒープ**を回す | O(n log k) |
| 全順序 | 比較ソート（マージ/クイック/ヒープ） | Θ(n log n)（比較ソートの下限） |
| 全順序・比較しない | 基数 / バケット / 計数ソート | O(n + 値域) ※比較しないので上の下限を回避 |

ペアワイズの max/min 同時取得（2n-2 → 3n/2）は「**冗長な比較を先に潰す**」という考え方。今回は N ≦ 50 なので実測差ゼロだが、発想は他で効く。

## 重複除去 (distinct) の選択肢

| 手法 | 計算量 | 使いどき |
|---|---|---|
| ハッシュ集合 (`HashSet`) | O(n) 期待 | 値域が広い・未知 |
| 直接アドレス表 (`bool[]`) | O(n + 値域) | 値域が小さく既知（今回 0..N-1, N≦50）← 最速 |
| ソートして隣接比較 | O(n log n) | 追加メモリを避けたい／順序も欲しい |

## 1パス化と loop fusion（ループ融合）

【B】の差分2でやっている「2周を1周にまとめる」は、近い名前の付いた有名な最適化がある。

### loop fusion とは

**loop fusion（ループ融合、別名 loop jamming）** = 複数のループを1つにまとめる変換。逆向きは **loop fission / loop distribution（ループ分割・分散）** で、この2つはペアで語られる。

狙いは3つ：

- **ループ自体のオーバーヘッド削減**（分岐と添字更新の回数が減る）
- **データ局所性の改善**（同じデータに触る処理をまとめるとCPUキャッシュに載ったまま処理できる）
- **中間配列の確保を消せる**（Julia などで大きな効果が出るのはここ）

### 人間がやるのか、コンパイラがやるのか → 両方

**コンパイラ最適化として**: LLVM に専用パス `LoopFuse` がある。ただし合法性の条件が厳しい。

- 2つのループが**隣接**している（間に文がない）
- **反復回数が一致**している
- **制御フロー等価**（一方が実行されるならもう一方も必ず実行される）
- 依存関係を壊さない

Oracle Studio、Intel コンパイラ、GCC（Graphite 経由）にも同種の機能がある。
**ただし実際にはほとんど発火しない。** Wikipedia は Clang 12.0.0 / GCC 11.1 の時点で「この loop fusion と余分な配列確保の除去は最高の最適化レベルでも起こらない」と明記している。コンパイラ任せにできる変換ではない。

**人間の手法として**: こちらが実用上のメイン。「**1パス化 / シングルパス / ストリーミング処理**」と呼ばれ、HPC・数値計算では定番。言語機能として持っているものもある。

| 仕組み | 何をしているか |
|---|---|
| Julia の broadcast fusion（ドット構文 `@. a + b * c`） | 式全体を1ループに融合。中間配列を作らない（言語機能） |
| Haskell / GHC の **stream fusion** | 中間リストを消す自動融合。Coutts+ ICFP 2007 の論文が有名 |
| Rust の Iterator / C++20 ranges / C# の LINQ | 遅延評価で中間コレクションを作らず1パスに畳む |

→ 同じ発想が「コンパイラ最適化」「言語機能」「手作業」の3レイヤーに現れる、と整理できる。

### 【B】は厳密には loop fusion ではない

教科書的な融合は「**同じ反復範囲の隣接する2ループ**を1つにする」もの。【A】→【B】はそこから外れている。

1. パス1は `(行 i, 列 j)` の**行優先**、パス2は `(列, 行)` の**転置順** → 反復順が違う（「隣接・反復回数一致」を素直には満たさない）
2. 中間配列 `priceMatrix` **そのものを消している**（これは deforestation / 中間データ除去の側）

これが成り立つ根拠は、**最小値が結合的・可換な畳み込み（reduction）**であること。だから値が流れてくる順に処理しても答えが変わらない。逆に言えば「順序に意味がある処理（累積和の途中結果を使う、など）」ではこの入れ替えはできない。

呼び名としては **1パス化 (single-pass) / ストリーミング化** の方が正確で、loop fusion はその親戚。そしてこれはまさに上の「コンパイラがやってくれない例」（融合＋配列除去）に該当する。

## 細かい話: `string.Split` のオーバーロード

`Split(" ")` と `Split(' ')` は実質同じ。どちらも区切り文字を配列で受け取らない単一引数のオーバーロードに束縛されるので、余分な配列確保は発生しない。

| 書き方 | 束縛されるオーバーロード |
|---|---|
| `Split(' ')` | `Split(char, StringSplitOptions = None)` |
| `Split(" ")` | `Split(string, StringSplitOptions = None)` |

「区切り文字用の配列が確保される」のは `params` 配列版に束縛されるとき、つまり `Split(new[]{' '})` や `Split(new[]{", ", "; "}, StringSplitOptions.None)` のような書き方。複数の区切り文字を渡したいときだけそちらになる。
